# 0016: Podman as a runtime of the virtual machine sandbox, and a review of Docker Desktop

Date: 2026-10-30

## Context

Decision 0014 left Podman out because none was installed on the machine it was built on, so neither its flags nor its signal proxying, its rootless user mapping and its mounts were checked. Ubuntu's runner for continuous integration ships Podman (4.9.3 on Ubuntu 24.04), and many Linux users have Podman and no Docker. This record adds it, and reviews the Docker adapter for anything that holds for OrbStack and not for Docker Desktop.

## Decision

`sandbox.runtime` (and `--sandbox-runtime`, and `sandbox_runtime` in the Model Context Protocol tools) accepts `podman` beside `docker` and `container`. Unset, the runtime is the first of docker, podman and container that answers, and on macOS the first of docker, container and podman, so a Podman machine that is running is not taken ahead of Apple's `container`, which was checked more. Podman runs the same way as Docker: one `podman run --rm -i`, the image by its ID, the relay and the bridge as decision 0014 describes them. The masks (with the one option below), the file mask's replacement of a directory with a read-only tmpfs and the bound entries, the limits, the probe (`EROFS` outside the state directory) and the stale-container removal are Docker's. This record gives what differs.

**What was read.** The Podman documentation at docs.podman.io (the latest version), for each flag the Docker adapter uses:

- `podman run` (https://docs.podman.io/en/latest/markdown/podman-run.1.html): `--network none` ("create a network namespace for the container but do not configure network interfaces for it"), `--read-only`, `--read-only-tmpfs` ("when running `--read-only` containers, mount a read-write tmpfs on /dev, /dev/shm, /run, /tmp, and /var/tmp. The default is true"), `--tmpfs` (default options `rw,noexec,nosuid,nodev`), `--mount type=bind` (`ro`, `readonly`, and `relabel`, with `z` and `Z` as shorthand), `--cap-drop`, `--security-opt no-new-privileges`, `--pids-limit`, `--memory` and `--memory-swap` ("not supported on cgroups V1 rootless systems"), `--log-driver` (`k8s-file`, `journald`, `none`, `passthrough`), `--pull` (`never`), `--env-file` ("a line-delimited file of environment variables"), `--sig-proxy` ("proxy received signals to the container process. SIGCHLD, SIGURG, SIGSTOP, and SIGKILL are not proxied. The default is true"), `--user` and `--userns` (`keep-id` "creates a user namespace where the current user's UID:GID are mapped to the same values in the container").
- `podman start` (https://docs.podman.io/en/latest/markdown/podman-start.1.html): `--sig-proxy` is true when attaching.
- `podman info` (https://docs.podman.io/en/latest/markdown/podman-info.1.html): `--format` takes a Go template over `.Host`, which holds `Arch` and `Security.Rootless`.
- `podman ps` (https://docs.podman.io/en/latest/markdown/podman-ps.1.html): `--all`, `--filter label=KEY`, `--format` with `.Names`, `.Labels` and `.Label`.
- `podman image inspect` (https://docs.podman.io/en/latest/markdown/podman-image-inspect.1.html): the `Id` is the 64 hexadecimal digits alone, with no `sha256:` prefix, where `Digest` has one.

**What was checked.** Podman 4.9.3 with crun 1.14.1, as Ubuntu 24.04 packages them (the versions on the Ubuntu runner), rootless, in a throw-away Ubuntu 24.04 container on the machine this was built on (nothing was installed on the host). The virtual machine acceptance suite ran on it with `BACTRIAN_VM_RUNTIME=podman`: 11 cases passed and 1 (the Seatbelt control, macOS only) was skipped, in 42.7 seconds, including the example agents in TypeScript and Python, the escape agents, a hidden file's neighbours, no host process visible, SIGINT, SIGKILL, bactrian with its bridge and client killed, the relay without heartbeats, and a stale container. Five findings disagree with the documentation or with Docker, and each is handled:

- A rootless Podman always uses a user namespace in which the host user is the container's root, and every other ID is a subordinate one that owns none of the project's files. With `--user 1001:1001` alone the agent saw the run's `0700` directories as root's and got `EACCES` on its own state directory. `--userns=keep-id` maps the agent's ID to itself, and with it the agent wrote its state directory. So a rootless Podman (`Host.Security.Rootless` in `podman info`) gets `--userns=keep-id`. A rootful one does not, because its container has no user namespace by default, so the user ID inside is the user ID outside. The rootful case was not run.
- `--tmpfs` copies what is beneath the mount point into the tmpfs by default (`tmpcopyup`), also when the mount point is inside a bind mount. A mask over `.bactrian` in a read-only bind of the project therefore showed the project's `.bactrian` unchanged, and the probe failed three checks (a masked file read, a denied file read, another run's directory). The documentation says to use `notmpcopyup` for a tmpfs that shadows a parent mount's subtree, so every mask is `--tmpfs PATH:ro,mode=0755,notmpcopyup`.
- With `--read-only` Podman mounts a writable tmpfs on `/dev`, `/dev/shm`, `/run`, `/tmp` and `/var/tmp` unless told not to. Docker's read-only root has two writable places, the `/tmp` that bactrian gives it and Docker's own `/dev/shm` (`rw,nosuid,nodev,noexec`, checked on OrbStack with bactrian's flags). `--read-only-tmpfs=false` turns Podman's off: `/x`, `/run/x` and `/var/tmp/x` all fail with `EROFS`, and `/tmp` is still the `noexec` tmpfs bactrian mounts. It also makes `/dev/shm` read-only (`libpod/container_internal_common.go` adds `ro` to the shared memory mount of a read-only container without `--read-only-tmpfs`, and on 4.9.3 a file there failed with `EROFS`), which would break POSIX shared memory and named semaphores (Python's `multiprocessing`, headless Chromium) under Podman alone. So Podman gets `--tmpfs /dev/shm:rw,noexec,nosuid,nodev,mode=1777,size=64m`, Docker's options with the 64 MiB that Docker Engine's and Podman's defaults give. Checked on 4.9.3, rootless: the agent's user writes `/dev/shm`, and `/dev` and `/run` stay read-only. The acceptance suite's shared memory case (a file in `/dev/shm` and a `multiprocessing.Lock`) runs on every runtime.
- `podman ps --format` rows in 4.9 have no `.Label` method (the documentation lists it for later versions): "can't evaluate field Label in type containers.psReporter". `{{index .Labels "KEY"}}` works, so that is what the stale-container listing uses for Podman. Docker's `.Labels` is one string, so Docker keeps `.Label`.
- The image ID has no `sha256:` prefix, as the documentation says. `podman run` and `podman image inspect` take it with the prefix, so bactrian keeps the prefix like Docker's and a run's label is the same in shape.

Also checked, and the same as Docker: the hidden `.env`, the read-only project, the writable state directory, `NoNewPrivs: 1`, an empty effective capability set, the environment file, input from a pipe, and `SIGTERM` to `podman run -i` reaching an agent that trapped it (exit status 7). `podman rm -f` waits ten seconds for a container whose first process ignores `SIGTERM`, as Docker's does not, and `--time 0` was left out because it failed with "given PID did not die within timeout" in one run. A relay stops on `SIGTERM` at once, so a bactrian container goes at once.

A rootless Podman keeps a container's runtime state under the directory that `XDG_RUNTIME_DIR` or `TMPDIR` names. A container made with one value cannot be stopped by a Podman started with another (the stop fails with "Error updating status ... EOF" and "given PID did not die within timeout"). The client environment keeps both (see below), so bactrian sees the user's own containers, and the acceptance suite passes both on to the `bactrian record` it starts.

**The command** is Docker's with `--userns=keep-id` (rootless only), `--read-only-tmpfs=false`, the `/dev/shm` tmpfs, `--http-proxy=false` and `--env-host=false` after `--security-opt no-new-privileges`, and `notmpcopyup` on each mask. The agent's user is `UID:GID` as for Docker, and the image is the ID `podman image inspect --format '{{.Id}}'` gave at the preflight (64 hexadecimal digits, with `sha256:` put before them), so a reference that moves between the check and the run cannot change the image.

**What else Podman adds.** `podman run` passes the proxy variables of the Podman service's own environment into the container (`--http-proxy`, true by default), and with `env_host` in `containers.conf` the whole of it (`--env-host`). With a Podman machine or a remote service those are the service's, and a proxy URL can hold credentials, which would break the environment allowlist. Both are switched off. Checked on 4.9.3: with `http_proxy=http://secret:pw@proxy:3128` in the client's environment a plain run showed it in the container, and a run with the two flags did not, also with `env_host=true` in a `containers.conf` (where `--http-proxy=false` alone was not enough). The same file's `env`, `volumes`, `mounts` and `devices` are not switched off by a flag: a `containers.conf` with `env = ["CONF=1"]` and a bind of a host directory put both in the container. Pointing `CONTAINERS_CONF_OVERRIDE` at a file that sets those four to empty arrays removed all of them, but bactrian does not write such a file (it would be one more file to keep and trust), so this is a residual risk (below).

**Detection** is `podman info --format '{{.Host.Arch}} {{.Host.Security.Rootless}}'`. On macOS the client talks to the Podman machine's service, so these are the machine's.

**The client's environment** is `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME` and, for Podman, `XDG_DATA_HOME` (where the rootless store is), `DBUS_SESSION_BUS_ADDRESS`, `CONTAINER_HOST`, `CONTAINER_CONNECTION`, `CONTAINER_SSHKEY`, `CONTAINERS_CONF`, `CONTAINERS_STORAGE_CONF`, `CONTAINERS_REGISTRIES_CONF` and `PODMAN_CONNECTIONS_CONF`. Never the provider keys (decision 0010). `CONTAINER_PASSPHRASE` and `SSH_AUTH_SOCK` are left out because they are credentials.

**The relay's build** uses a fully qualified Alpine reference (`docker.io/library/alpine:...@sha256:...`), because Podman resolves an unqualified name through the user's registries configuration and may refuse to guess. Docker and container read the qualified name as the same image (checked: Docker gives the same image ID, and Apple's `container` 1.5.0 ran the image by that reference; the relay itself was cached on this machine, so the build ran on neither). A rootless Podman's container root is the host user, and the host user's ID is a subordinate ID inside, so the build leaves out the `chown` that gives the relay to the user.

**The environment file.** The Podman documentation says only "a line-delimited file of environment variables". Its reader is `ParseFile` and `parseEnv` in `pkg/env/env.go` of containers/podman (v4.9.3, read in source): a `bufio.Scanner` with the 64 KiB token limit (bactrian's longest line, 65535 bytes, fits), leading spaces and tabs trimmed from a line, lines starting with `#` skipped, a line split at its first `=`, and a `NAME*` or bare `NAME` taken from the client's environment only when the line has no `=`. A run with `A=b` in it passed the variable to the agent. bactrian's own refusals (line breaks of every kind, NUL, `#` names, whitespace in a name, an empty name or one holding `=`, more than 64 KiB, invalid UTF-8) apply to all three runtimes and are written as strictly as the strictest reader (decision 0015), and every line it writes has a `=` and a name without whitespace, so none of Podman's special cases (the trimmed indent, the comment, the expansion from the client's environment) can apply, and a name or value that reaches the file is one all of them read the same way.

**Signals.** `podman run` proxies `SIGTERM` and `SIGINT` to the container by default, so the bridge needs no `signals=kill` word, as for Docker. A killed client leaves the container running, as with Docker, and the relay's heartbeat, the bridge's watch on its parent and the removal of stale containers cover that.

## Docker Desktop

Docker Desktop is not installed on the machine this was built on, so nothing below was run against it. The adapter was read for what OrbStack does and Docker Desktop may not, against Docker's settings page (https://docs.docker.com/desktop/settings-and-maintenance/settings/):

- **Socket and context.** Docker Desktop creates `/var/run/docker.sock` only when a setting asks for it ("which some third party clients may use"), so a plain `docker` client may reach Docker Desktop only through a context stored in `~/.docker`. The client's environment holds `HOME`, `DOCKER_CONFIG`, `DOCKER_CONTEXT` and `DOCKER_HOST`, so a context resolves as it does in the user's shell. No socket path is built by bactrian. The location of the context's socket was not checked.
- **File sharing.** Docker Desktop mounts only the folders it shares ("by default the `/Users`, `/Volumes`, `/private`, `/tmp` and `/var/folders` directory are shared", with VirtioFS the default implementation), where OrbStack shows the whole host. Every host path of a run is under the project, the run's directory or `~/.cache/bactrian/relay`, all resolved with `realpath` before they enter the command (so `/tmp` is `/private/tmp`). A project outside the shared folders fails at the preflight with Docker Desktop's own error ("Mounts denied: The path ... is not shared from the host"), which the message carries (that wording is from memory, not from the documentation).
- **Host networking.** The container has `--network none` and reaches bactrian only through the relay's frames on standard input and output, so nothing depends on `host.docker.internal` or on how Docker Desktop routes to the host.
- **Bind mounts and ownership.** The state and temporary directories are mode `0700`, owned by the user, and the agent runs as `--user UID:GID`. On OrbStack the agent can use them (tested). Docker Desktop's file sharing maps ownership by its own rules, so if the agent cannot, the preflight probe's write to the state directory fails and the sandbox is refused (fail closed).
- **Image store.** The setting "uses containerd image store instead of classic image store" and its default is enabled. With it `docker image inspect --format '{{.Id}}'` may give the digest of the image index or manifest rather than of the configuration (not checked). The preflight needs only the `sha256:` prefix and `docker run` taking the value, which was not run.
- **Docker Desktop for Linux.** Its daemon is in a virtual machine and its socket is per user (`~/.docker/desktop/docker.sock`, reached through the `desktop-linux` context), not `/var/run/docker.sock`, and its file sharing maps ownership by its own rules. Not run. The client's environment carries the context as for macOS, so no path is built by bactrian, and a mapping that hides the project or its `0700` directories fails the probe.
- **Rootless Docker.** A Docker daemon run by a user lives in a user namespace like a rootless Podman, so `--user UID:GID` is a subordinate ID that owns none of the project's files and the agent gets `EACCES` on the `0700` directories, the failure that `--userns=keep-id` fixes for Podman. Docker has no flag of that kind, and the adapter takes `rootless` as false for Docker (it does not ask `docker info`). Not run, by analogy with Podman. It fails closed at the preflight probe. Use rootless Podman, or a rootful Docker, on such a host.
- **The `podman-docker` package** makes `docker` a link to Podman. `runtime: docker` then fails the architecture query, because `podman version --format '{{.Server.Arch}}'` is an error in 4.9.3 ("can't evaluate field Arch in type *define.Version"), and the message blames the daemon. Set `runtime: podman`, which is what the not-on-PATH message for docker now says.
- **Nothing changed in the Docker code.** No difference found in the code needed a fix. The unverified points above are listed so a run on Docker Desktop checks them: the acceptance suite (`dune build @acceptance`) is the test.

## Consequences

On Linux, Podman is a working runtime for the virtual machine sandbox with no Docker. The acceptance suite of the virtual machine runs on Podman in continuous integration, on Ubuntu 24.04's runner (pinned, because 4.9.3 is what was checked and `ubuntu-latest` will move on), with `BACTRIAN_VM_RUNTIME=podman`. The output of that job is the only verification of the runner's own Podman (rootless set-up, cgroup controllers and AppArmor), which differs from the throw-away container used here.

Residual risks and limits, on top of decision 0014's:

- **SELinux.** On a host where SELinux is enforcing (Fedora, RHEL), a bind mount of the project is not readable by the container unless it is relabelled. `relabel=private` (`Z`) would change the labels of the user's project, and `--security-opt label=disable` would drop the confinement, so bactrian does neither. The preflight fails with Podman's message. Not run, since no SELinux host was available.
- **The Podman machine on macOS and Windows** (a remote client, the project shared through the machine's mounts, rootful or rootless) was not run. The code takes rootless from `podman info`, which the remote client answers for the machine.
- **Control groups.** `--pids-limit`, `--memory` and `--memory-swap` need the controllers delegated to the user. When they are not, a rootless Podman does not always refuse. Its documentation says `--memory` is "not supported on cgroups V1 rootless systems". In the throw-away container (control groups version 2, the cgroupfs manager), with the pids controller left out of the user's control groups in three ways, the same run with all three flags had three outcomes: it exited 0 with no message and neither limit (no `pids.max`, and `memory.max` was `max`), crun enabled the controller itself and both limits held, or crun stopped it ("the requested cgroup controller `pids` is not available"). `podman info`'s `CgroupControllers` did not predict them (it gave `[]` in a layout where `--memory` was applied), so it is no check. The probe therefore reads the container's own `pids.max` and `memory.max` (or version 1's `pids/pids.max` and `memory/memory.limit_in_bytes`), and under Docker and Podman the sandbox is refused unless they are 1024 and 4294967296, with a message that names the flag the runtime dropped. That covers a rootless Docker too. `container` is not checked this way, because it limits processes per user and its memory is the virtual machine's. Swap is not read, so `--memory-swap` is still taken on trust.
- **`containers.conf` and `mounts.conf`.** Podman reads `containers.conf` (system, the user's, and `CONTAINERS_CONF`, which the client's environment passes on), and its `[containers]` `mounts`, `volumes`, `devices`, `env` and `env_host` apply to every run, and `/etc/containers/mounts.conf` (the default on RHEL, for `/run/secrets`) adds mounts. They can show the agent more than the project and add variables to its environment, and the probe checks fixed paths, so it would not see an extra mount. With a Podman machine or a remote service it is the service's file. The user's own configuration is the user's to trust, and `CONTAINERS_CONF_OVERRIDE` pointing at empty arrays is the way to switch it off (checked on 4.9.3), but bactrian does not do that for them.
- **Short image names.** An image named without a registry (`node:24-alpine@sha256:...`) is looked up in Podman's store through its short-name rules. Name the registry (`docker.io/library/node:...`) to be sure.
- **Root.** A bactrian run as root (user ID 0) with a rootless Podman is not a case that was checked. A rootful Podman runs the agent as user ID 0 like Docker.
